# 5.8: Rimuovere i marker di conflitto git committati nel modulo UI

**Story ID:** 5.8
**Epic:** 5 — Code Quality & Infrastructure
**Slug:** merge-conflict-markers-cleanup
**Status:** done
**Created:** 2026-08-18
**Updated:** 2026-08-18

## Story

Come **agente che deve verificare il proprio lavoro con PHPStan**,
voglio **che nessun file del modulo `UI` contenga marker di conflitto git**,
così **`analyse Modules` produce un elenco di errori invece di fermarsi su 6 `phpstan.parse`**.

Un errore `phpstan.parse` è marcato `non-ignorable`: finché resta, l'analisi non è
attendibile per nessun altro file e il lavoro di verifica di tutti gli agenti in
parallelo è azzerato.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. `git grep -ln '^<<<<<<< \|^>>>>>>> ' -- 'Modules/**/*.php'` non restituisce nulla.
2. `php -l` passa su tutti i file toccati.
3. Ogni conflitto è risolto scegliendo la variante coerente con il **codice circostante** (classe base, classi sorelle, file gemelli), non con la posizione nel diff: la motivazione di ciascuna scelta è scritta.
4. Nessun file viene riscritto per intero: le modifiche sono chirurgiche sui soli blocchi in conflitto. `git diff HEAD | grep "^-.*function "` non mostra funzioni sparite oltre a quelle esplicitamente rimosse.
5. La struttura del file di lingua `table_layout_enum.php` rispetta la convenzione degli enum del progetto (chiave `values`).

## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

- **`T_SL` è `<<`.** `Syntax error, unexpected T_SL` non è un errore di sintassi PHP esotico: è la prima riga di `<<<<<<< HEAD`. Tutti e 9 i file provenivano dallo stesso commit di merge (`92912795`).
- **Blocks → `getFormSchema`.** I Block estendono `XotBaseBlock`, che non ha nulla a che vedere con `XotBaseResource`: il rename `getFormSchemaOld` riguarda solo la gerarchia Resource. I Block fratelli non toccati dal conflitto (`Post`, `Image`, `Category`, `Contact`) usano tutti `getFormSchema`. [Source: docs/wiki/filament/xotbaseresource-formschema-old-pattern.md §«Cosa NON rinominare»]
- **`GroupColumn` → `return;`.** Senza `return`, `if (null === $table) { }` prosegue e chiama `$child->table(null)` su ogni figlio: la guardia esisteva proprio per evitarlo.
- **`table_layout_enum.php` → `values`.** `Xot/lang/it/gender_enum.php`, `yes_no_enum.php` e il gemello `UI/lang/it/table-layout-enum.php` usano tutti il wrapper `values`. La variante senza wrapper era l'unica anomalia.
- **Asset → `branding`.** Nessuno dei due file esiste su disco, quindi il filesystem non decide. Decide l'architettura: `UI` è un modulo riusabile e non deve contenere il nome di un progetto specifico nei percorsi.
- **`fixcity_data.sqlite`.** È il database di test condiviso già usato da `Xot/tests/TestCase.php`, `Job/tests/TestCase.php` e `Lang/tests/TestCase.php` (verificato sul codice attuale, non sulla nota originale del 18 agosto: nel frattempo il file condiviso è stato rinominato da `ptv_data.sqlite`). La variante `database.sqlite` compariva inoltre duplicata su due righe, segno di un merge malriuscito e non di una scelta.
- **`ptv_data.sqlite`.** È il database di test condiviso già usato da `Xot/tests/TestCase.php`, `Job/tests/TestCase.php` e `Lang/tests/TestCase.php`. La variante `database.sqlite` compariva inoltre duplicata su due righe, segno di un merge malriuscito e non di una scelta.
- **`$currentValue = $currentValue;`** è un no-op che lascia la variabile non definita al primo render, mentre `?? null` la inizializza: la variante «HEAD» era il bug.
