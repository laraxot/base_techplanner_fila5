# Story: UI PHPStan fix

## Story

Come owner UI, voglio che `Modules/UI` sia PHPStan-green (0 errori reali) seguendo il
workflow "PHPStan zero" (`bashscripts/docs/prompts/03-quality-gates.md`), senza ignore,
baseline, o modifiche a `phpstan.neon`.

## Baseline (2026-09-07, sessione corrente)

All'avvio sessione il modulo aveva gia' un working tree condiviso con WIP non mio: 7 file
in `app/Filament/Blocks/` (`Category.php`, `Contact.php`, `Image.php`, `Navigation.php`,
`Page.php`, `Post.php`, `Slider.php`) con `getFormSchema()` convertito da
`public static function` a `public function`, allineandosi alla convenzione repo-wide
(`$this->getFormSchema()`, usata in `XotBaseResource`, `XotBasePage`, `XotBaseWidget`,
`XotBaseRelationManager`). Nessun claim attivo trovato in `docs/chat/INDEX.md` ne' lock
attivo (`bash bashscripts/lock/check.sh laravel/Modules/UI` → FREE).

`./vendor/bin/phpstan analyse Modules/UI --no-progress --memory-limit=-1`:

**4 errori reali**, tutti `method.staticCall` ("Static call to instance method"):

- `tests/Unit/UiGapCloser100Test.php:151` — `Image::getFormSchema()`
- `tests/Unit/UiHighestMissCoverageTest.php:180` — `Contact::getFormSchema()`
- `tests/Unit/UiHighestMissCoverageTest.php:181` — `Category::getFormSchema()`
- `tests/Unit/UiHighestMissCoverageTest.php:182` — `Post::getFormSchema()`

Causa radice: i due file di test chiamavano ancora `Block::getFormSchema()` in modo
statico, mentre il metodo (nel WIP gia' presente) e' ora un'istanza. Il WIP sorgente e'
corretto e coerente con la convenzione del framework (verificato con
`grep -rn "getFormSchema()"` su `Modules/Xot`: sempre `$this->getFormSchema()`, mai
statico); la causa radice reale del PHPStan error era nei call-site di test rimasti
indietro, non nel WIP.

## Acceptance Criteria

1. `./vendor/bin/phpstan analyse Modules/UI --no-progress --memory-limit=-1` → 0 errori.
2. Nessun `@phpstan-ignore`, nessuna baseline, nessuna modifica a `phpstan.neon`.
3. Nessun `mixed` introdotto.
4. Root cause fix (call-site dei test), non soppressione del sintomo.
5. Coverage/test status non regredito rispetto all'ultima baseline onesta nota
   (`7.13.mixed-type-reduction.story.md`, 2026-09-04: 197 passed/8 failed pre-esistenti).

Tutti soddisfatti — vedi `docs/coverage.md`.

## Fix

In `tests/Unit/UiGapCloser100Test.php` e `tests/Unit/UiHighestMissCoverageTest.php`,
sostituite le chiamate statiche con istanziazione esplicita:

```diff
- Assert::assertNotEmpty(Image::getFormSchema());
+ Assert::assertNotEmpty((new Image())->getFormSchema());

- Assert::assertNotEmpty(Contact::getFormSchema());
- Assert::assertNotEmpty(\Modules\UI\Filament\Blocks\Category::getFormSchema());
- Assert::assertNotEmpty(Post::getFormSchema());
+ Assert::assertNotEmpty((new Contact())->getFormSchema());
+ Assert::assertNotEmpty((new \Modules\UI\Filament\Blocks\Category())->getFormSchema());
+ Assert::assertNotEmpty((new Post())->getFormSchema());
```

Nessun altro file toccato dentro questa story (i 7 file `Blocks/*.php` erano gia' dirty
per WIP altrui non attribuibile a questa sessione; non fanno parte del commit di questa
story — vedi `docs/chat/2026-09-07-phpstan-ui-done.md` per la nota di scope sul git add
selettivo).

## Aggiornamento 2026-09-10 (recidiva sullo stesso pattern)

Nuova sessione, task scoped a "PHPStan errori residui Modules/UI" (42 errori totali
repo-wide assegnati ad altre sessioni; qui solo la fetta UI). Verifica preliminare
(`./vendor/bin/phpstan analyse Modules/UI --no-progress --memory-limit=-1`) mostrava
**2 errori reali**, stesso identifier `method.staticCall`, stesso pattern del
2026-09-07 ma su `Modules\UI\Enums\FieldTypeEnum::getFormSchema()` (metodo di istanza
ereditato da `Modules\Xot\Traits\EnumTrait::getFormSchema()`, non da `Filament\Blocks`):

- `tests/Unit/UiCoverageBoostTest.php:19` — `FieldTypeEnum::getFormSchema()` statico.
- `tests/Unit/UiFilamentComponentsCoverageTest.php:63` — idem.

Le altre call-site segnalate nel context iniziale del task (`TestCase.php:67`
`prepareSharedFixcitySqliteForTesting`, `UiGapCloser100Test.php`,
`UiHighestMissCoverageTest.php`) risultavano gia' verdi: corrette da un'altra sessione
concorrente prima di questo run — saltate, nessun edit necessario.

### Fix applicato

```diff
- $schema = FieldTypeEnum::getFormSchema();
+ $schema = FieldTypeEnum::TEXT->getFormSchema();
```

Applicato identico in entrambi i file. Il metodo (`EnumTrait::getFormSchema()`, riga 57)
usa internamente `static::cases()`, quindi il case scelto per l'istanziazione non
influenza il risultato: `TEXT` e' usato solo come receiver valido.

### Verifica

`./vendor/bin/phpstan analyse Modules/UI --no-progress --memory-limit=-1` → `[OK] No errors`.

### PHPStan: blocco di bootstrap esterno, poi 0 errori

Primo run, `cd laravel && ./vendor/bin/phpstan analyse Modules/UI --no-progress --memory-limit=-1`:
**bootstrap fallito** (non un report PHPStan normale) — `Application bootstrap failed`,
`syntax error, unexpected token "<<", expecting end of file`. Diagnosi (sola lettura,
nessun file editato fuori da `Modules/UI`): con Larastan il bootstrap carica l'intera
app Laravel (tutti i config/provider di tutti i moduli abilitati), quindi un solo file
rotto in un ALTRO modulo blocca l'analisi PHPStan di QUALSIASI modulo, `Modules/UI`
incluso. Causa reale isolata via scan mirato (`php -l` su `Modules/**/*.php`, sola
lettura): marker/residui di merge non chiusi in
`Modules/IndennitaCondizioniLavoro/{tests/Pest.php,tests/TestCase.php,config/config.php}`
— modulo assegnato a un altro agente dello swarm, esplicitamente fuori dal mio scope
(`NON toccare... mai altri Modules/Themes`). Non modificato da me. Un secondo run,
pochi minuti dopo, ha confermato che l'agente owner di quel modulo lo aveva gia'
risolto nel frattempo (nessun marker residuo, `php -l` pulito sui 3 file).

Secondo run, bootstrap ok:

```
cd laravel && ./vendor/bin/phpstan analyse Modules/UI --no-progress --memory-limit=-1
[OK] No errors
```

**0 errori reali in `Modules/UI`.** Nessun fix necessario in questa sessione: lo stato
"PHPStan zero" raggiunto dalle sessioni 2026-09-07/2026-09-10 (sopra) e' confermato
ancora valido oggi.

### Pattern per il second brain (non ovvio, riutilizzabile)

Un `Application bootstrap failed` di PHPStan/Larastan con path tipo
`Modules/<Altro>/...` nello stack trace **non e' un errore del modulo che si sta
analizzando**: Larastan bootstra l'intera applicazione (tutti i moduli abilitati),
quindi qualunque modulo con un file di config/test rotto blocca l'analisi scoped di
*tutti* gli altri moduli contemporaneamente. In uno swarm con 21 agenti paralleli
questo produce un falso allarme diffuso ("il mio modulo non compila") quando la causa
reale e' un singolo modulo terzo con un merge marker non chiuso. Diagnosi rapida e
sicura (sola lettura, nessun edit fuori scope):
`find Modules Themes -name "*.php" -print0 | xargs -0 -P4 -n1 -I{} sh -c 'php -l "{}" || true'`
filtrando `grep -v "^No syntax errors detected"` — isola il file/modulo colpevole senza
eseguire ne' modificare nulla fuori dal proprio scope, e permette di ri-lanciare phpstan
in attesa che l'agente owner risolva, invece di provare workaround (mai `-c`/exclude
path: rischia di mascherare il bug reale per gli altri 20 agenti).

### Learnings from Previous Stories

- [Source: `bashscripts/ai/wiki/memories/getformschema-static-to-instance-and-table-trans-gotchas.md`,
  esteso in questa sessione] Quando un metodo `getFormSchema()`/hook XotBase passa da
  static a instance in una classe (anche fuori dalla gerarchia Resource, es.
  `Filament/Blocks/*.php`), verificare SEMPRE i call-site nei test: PHPStan segnala solo
  la direzione "static call su metodo instance" (`method.staticCall`), non il contrario
  (chiamare un metodo static via `->` e' PHP valido e PHPStan non lo segnala di default) —
  quindi il fix nei test (`(new Xxx())->getFormSchema()`) e' sicuro in entrambe le
  direzioni, anche se il fix del metodo sorgente e' ancora WIP di un'altra sessione.

### Sessione 2026-09-10

  (es. `FieldTypeEnum`). Stesso fix, stesso identifier PHPStan, call-site diversi.
